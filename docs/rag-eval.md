# 检索召回评测

度量 RAG 代码库检索的召回质量，用来回答「混合权重为什么取 0.7 / 0.3」。

入口 `POST /rag-eval/run`，标注集在 `src/main/resources/eval/rag-eval-set.json`。

不复用 `/eval/run`：评测跑批用负数 appId，检索链路的三处闸门会整体跳过，跑批出来的通过率与检索质量无关。原因见 `design-notes.md` 第四节。

## 一、指标

全部按文件级计算。用户说「改一下导航栏」时，他指向的是一个文件，不是某几行；按片段级算会把命中了同一文件的其它片段判成漏召，分数低于真实体验。

| 指标 | 定义 |
|---|---|
| `Recall@K` | 期望文件集合中，出现在 Top-K 结果里的比例（K = `app.rag.top-k`，默认 8） |
| `Precision@K` | Top-K 结果的文件中，属于期望集合的比例 |
| `MRR` | 第一个命中期望文件的排名倒数（命中在第 3 位记 1/3） |
| `Top-1` | 期望文件排在首位的用例条数 |
| 命中率 | 至少命中一个期望文件的用例占比 |

同一文件返回多个片段只算一个文件，原始片段数会一并输出，用来判断 `max-chunks-per-file` 是否生效。

这份标注集里 `Precision@K` 与命中率是退化指标，不要拿它们判断质量：

- 每条用例只有 1 个期望文件，于是 `Precision@K` 恒等于 `1 ÷ 返回文件数`。首轮实测的 21.4% 与逐条 `1/len(实得)` 吻合，它衡量的是工程规模。
- 命中率恒等于 `Recall@K`，分子都是「至少命中一个」。

看排序质量用 MRR 与 Top-1，看有没有捞到用 `Recall@K`。前提是工程文件数远多于 K，只有 14 个文件而 K=8 时，`Recall@8` 接近必然成立。

## 二、标注集

**v1.1，2 个应用 28 条用例（点名 8 + 语义 20）。**

被测工程是平台上真实生成并落盘的两个 Vue 工程（云雾山旅游站、潮玩手办馆），不是专门造的样本，检索面对的分布才与线上一致。

用例分两类，必须分开统计：

- **POINTED（点名型，8 条）**：需求里直接写了文件名，如「把 Navbar.vue 的导航项改掉」。靠文件名加成与关键词即可命中，是最理想也最不真实的情况。
- **SEMANTIC（语义型，20 条）**：需求只描述功能、不含任何代码标识符，如「页面向下滚动之后顶上那条导航栏的背景要变成不透明的白色」。这是用户真实的表达方式。

混在一起算平均会让点名型的高分掩盖语义型的短板，进而得出「关键词已经够用、向量没有价值」这种与事实相反的结论。

语义型取 20 条是按显著性反推的，要 6 个不一致对才跨过 p<0.05，推导见 `design-notes.md` 第四节。

### 加载时的校验

`RagEvalSetLoader` 在配置期严格校验：appId 非正数、appKey 不存在、expectedFiles 为空、路径跳出工程根、id 重复，任一不满足直接抛错。

对 SEMANTIC 用例另有一条：query 里不得出现文件名线索（`.vue`、`.js` 等）或驼峰标识符（`localStorage`、`Navbar`）。一条语义型用例只要写了文件名，就退化成关键词题却仍被算进语义型的分母，指标会悄悄变好。点名型不受此约束，写文件名正是它的本分。

## 三、怎么跑

在真实运行环境下（IDEA 里启动，`LLM_BASE_URL` / `LLM_API_KEY` 已注入）：

```
GET  /rag-eval/set                 先看一眼用例与期望文件，标注写错的话后面全是白跑
POST /rag-eval/run?ablation=true   跑三组权重消融（默认）
POST /rag-eval/run?ablation=false  只跑线上生效的那组权重，省 2/3 调用
```

跑完报告同时返回并打进日志，形如：

```
┌─ 代码检索召回评测 ────────────────────────────────────────────
│ 评测集：代码检索召回评测集 v1.1，用例 28 条
│ 参数：topK=8，单文件片段上限=3，通用文件折扣=1.0（关闭）
│ 索引：云雾山旅游站(N 片段) 潮玩手办馆(N 片段) ，耗时 N ms
│ 向量：可用
└───────────────────────────────────────────────────────────────

【总体对照】同一批索引与查询，差异只来自权重
  配置              Recall@8   Precision@8  MRR     命中率
  仅关键词(0/1)     ...
  仅向量(1/0)       ...
  混合              ...
  ⚠ Precision@K 在「每条用例只有 1 个期望文件」时恒等于 1 ÷ 返回文件数，……

【分组对照】点名型靠文件名即可命中，语义型才是向量该发力的地方
  配置              分组      Recall@8   MRR      Top-1
  混合              点名型      ...       ...       ...
  混合              语义型      ...       ...       ...

【向量是否真的参与打分】只在两组权重都非 0 的配置下才有意义
  混合              链路检查：28/28 条用例的 top-1 片段向量分 > 0（=0 说明向量根本没进排序）
                    强证据：N/28 条用例的 top-1 关键词分为 0 —— 这些用例的首位排名只能来自向量

【漏召清单】用来定位「哪条用例、在哪组权重下捞不到期望文件」
  混合              漏召 N 条：...

【排后清单】期望文件进了 Top-K 却没排首位：看榜首被谁占走
  混合              排后 N 条，榜首占位：<文件>×N、...
```

上面这张是格式示例，数字与文件名一律留成 `...` 与 `N`。真实数字每隔一轮就会变，写死在这里的迟早变成又一份过期口径，连索引耗时也一样。

## 四、怎么读结果

按这个顺序看。

1. **索引片段数。** 有任何一个应用是 0，后面所有指标必然是 0，这是链路问题不是算法问题。
2. **「向量」那行。** 显示不可用说明 embedding 凭证有问题，此时全部指标退化为纯关键词，而「仅关键词」恰好也是消融里的一组，两者会混为一谈。
3. **「向量是否真的参与打分」，只有混合组的那两行有意义。**
   - 仅关键词组整块显示「不适用」。它的向量分算得出来，只是权重为 0、没进总分，照常印「N/N 条向量分 > 0」会让人以为向量参与了排序，而那恰恰是唯一没参与的一组。
   - 仅向量组的第二行也显示「不适用」。该组关键词权重为 0，榜首全部由向量决定，统计出其中几条反而会暗示其余是关键词顶上来的。
   - 混合组里，第一行（向量分 > 0）只是链路检查，向量可用时它必然等于用例总数，不构成证据；第二行（top-1 关键词分为 0 的条数）才是证据，这些用例的首位不可能是关键词推上去的。若这个数长期为 0，说明榜首全是字面命中拿下的。
4. **漏召清单与排后清单，必须分开看**，因为要采取的行动不一样。
   - 漏召：期望文件没进 Top-K，按配置列出用例号，回答「这一条到底是谁不行」。只给百分比看不出是哪几条在拖后腿。
   - 排后：期望文件进了 Top-K 但没排首位，按配置汇总榜首被哪个文件占走，回答「该治哪个文件」。若榜首长期是同一两个对谁都像的文件（全局样式、首页、关于页），那是通用文件淹没，该治的是它，不是继续调权重。按占位文件汇总而不是列用例号，正是因为要修的是那个文件。
   - 两者的差值是同一批用例在两个状态之间的迁移，只报单一清单会得出相反结论。
5. **分组对照，重点是语义型那一列。**
   - 若仅关键词在语义型上已经很高，说明这批查询的词面与代码重合度高，该补的是更不像代码的查询，而不是宣布向量无用。
   - 若仅向量在点名型上很差，说明 `FILE_MENTION_BONUS` 确实在起作用。
   - 混合应当在两类上都不差于任一单路，否则权重需要调整。
   - 语义型的短板通常不在 Recall 而在 MRR / Top-1，捞到了但排在第三、第四位。Top-K 够大时这不影响最终结果（片段照样进上下文），但它决定了将来要不要为省 token 把 topK 调小。

## 五、成本

| 阶段 | 调用次数（约） |
|---|---|
| 建索引（两个工程，首次） | 10 次 |
| 每条用例检索一次 | 1 次 |
| 全量消融 28 条 × 3 组 | 84 次 |
| **合计** | **约 94 次** |

`app.budget.max-calls` 必须大于这个量级。闸门耗尽时每条用例都返回空列表，报告里表现为召回率突然全线归零，很容易被误读成检索退化。

增量索引会大幅降低重复跑的成本：文件没变时 `fileHash` 比对通过，不会重新向量化。

## 六、已知边界

- **`max-chunks-per-file=3` 会压缩 Top-K 的文件覆盖数。** 一条需求的期望文件超过 3 个时，可能因为配额而永远召不全，这不是检索算法的问题。标注时单条需求建议不超过 3 个期望文件。
- **语义型查询难以完全避开词面重合。** 即便刻意用同义改写，「留言」「分类」这类词仍可能出现在代码里，关键词路径依然能命中。这是真实的分布，不做人为美化。
- **点名型用例在 `topK ≥ 工程文件数` 时没有鉴别力。** `topK=8`，两个工程各 10 来个文件，期望文件不论排第几都会进结果，于是三组（含仅关键词）一律 100% / MRR 1.000 / Top-1 8-8。这不是关键词够用的证据，是任务太简单的证据。要让它有鉴别力，必须让需求里出现相似竞争文件。
- **「内容在数据文件、改动在展示文件」的需求会被系统性误召。** 用例 16 三组全漏即是此例：改动落在 `Detail.vue`，但尺寸数据在 `products.js`，且后者相关片段密度更高。
- **评测会改写全局权重配置。** `RagEvalRunner` 在 `finally` 里还原，若进程在还原前被杀，重启前线上的权重视为被改动过。
- **评测结果不落库。** 这是实验数据不是运营数据，跨批次比较靠记录报告即可。
