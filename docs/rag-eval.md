# 检索召回评测

度量 RAG 代码库检索的召回质量，并回答「混合权重为什么取 0.7 / 0.3」。

## 一、为什么不复用代码生成评测

**`POST /eval/run` 拿不到任何 RAG 数据，这是设计使然而不是遗漏。**

评测跑批用的是负数 appId（`EvalScope`），而检索链路上有三处闸门都会因此直接跳过：

| 位置 | 条件 | 后果 |
|---|---|---|
| `CodeRetriever#retrieve` | `appId <= 0` | 直接返回空列表 |
| `CodeIndexService#indexAfterGeneration` | `appId <= 0 \|\| EvalScope.isActive()` | 不建索引 |
| `CodeIndexService#ensureIndexed` | `appId <= 0` | 不建索引 |

这个隔离是对的 —— 它保证「生成评测」的口径跨版本可比（否则 metrics 会随 RAG 开关漂移）。
但它同时意味着：**跑批出来的通过率、自愈轮次，与检索质量毫无关系**，
`mvn test` 里的单测更不可能覆盖（全程 mock，且测试环境的数据源是假值）。

所以检索质量必须单独测，用真实的正数 appId 与真实的产物工程。

## 二、指标定义

全部按**文件级**计算 —— 用户说「改一下导航栏」时，他指向的是一个文件，不是某几行。
按片段级算会把「命中了同一文件的其它片段」判成漏召，分数低于真实体验。

| 指标 | 定义 |
|---|---|
| `Recall@K` | 期望文件集合中，出现在 Top-K 结果里的比例（K = `app.rag.top-k`，默认 8） |
| `Precision@K` | Top-K 结果的文件中，属于期望集合的比例 |
| `MRR` | 第一个命中期望文件的排名倒数（命中在第 3 位记 1/3） |
| `Top-1` | 期望文件排在首位的**用例条数**（MRR 把它揉成一个平均数，条数才能定位） |
| 命中率 | 至少命中一个期望文件的**用例**占比（与 Recall 不同：前者数用例，后者按文件比例） |

同一文件返回多个片段只算一个文件；但原始片段数会一并输出，
用来判断 `max-chunks-per-file` 是否起了作用。

⚠️ **本标注集里 `Precision@K` 与 `命中率` 是退化指标，别拿它们判断质量**：

- 每条用例只有 1 个期望文件（见第三节），于是 `Precision@K` 恒等于 **1 ÷ 返回文件数**
  —— 首轮实测的 21.4% 与逐条 `1/len(实得)` 逐条吻合，它衡量的是工程规模而不是检索质量；
- 同理 `命中率` 恒等于 `Recall@K`（分子都是「至少命中一个」）。

看排序质量请用 **MRR 与 Top-1**，看「有没有捞到」请用 `Recall@K`
（前提是工程文件数远多于 K —— 只有 14 个文件而 K=8 时，`Recall@8` 接近必然成立）。

## 三、标注集

`src/main/resources/eval/rag-eval-set.json`，**v1.1，2 个应用 28 条用例**（点名 8 + 语义 20）。

被测工程是平台上**真实生成并落盘**的两个 Vue 工程（旅游站 / 手办商城），
不是专门造的样本 —— 检索面对的分布才与线上一致。

用例刻意分两类，**必须分开统计**：

- **POINTED（点名型，8 条）**：需求里直接写了文件名（「把 Navbar.vue 的导航项改掉」）。
  靠文件名加成与关键词即可命中，这是最理想也最不真实的情况。
- **SEMANTIC（语义型，20 条）**：需求只描述功能、不含任何代码标识符
  （「页面向下滚动之后顶上那条导航栏的背景要变成不透明的白色」）。
  这才是用户真实的表达方式，也是向量检索存在意义的所在。

**混在一起算平均会让点名型的高分掩盖语义型的短板**，进而得出
「关键词已经够用、向量没有价值」这种与事实相反的结论。

### 语义型为什么是 20 条而不是 8 条

**为了够得着「显著」这条线，不是为了数字好看。**

配对比较只看**不一致对**（同一条用例两组「一组捞到、一组没捞到」）。
v1.0 的 8 条语义型实测：仅关键词 4/8、仅向量 7/8，不一致对只有 **3 个且全部偏向向量**。
两侧符号检验：

| 全偏向向量的不一致对 | 3（v1.0 现状） | 4 | 5 | **6** | 7 |
|---|---|---|---|---|---|
| 两侧 p | **0.2500** | 0.1250 | 0.0625 | **0.0312** | 0.0156 |

⇒ **要 6 个不一致对才跨过 p<0.05**。8 条样本下单条用例摆动 12.5 个百分点，
再往下比较就是在拟合噪声。扩到 20 条，才有机会把「方向明确」升级成「统计显著」。

> **实测兑现了（见第十节）**：扩到 20 条后，不一致对恰好 **6 个且全部偏向向量**，p = 0.031。
> 这个「20 条」不是随口定的整数，是先算出阈值反推出来的样本量。

> **扩样本时新用例要覆盖「中间地带」。** v1.0 里 `kw=0` 的极端样本（05、13）是
> 词面与代码完全不重合的情形，最能拉开差距的其实是**语义型但词面有轻微重合**的那批 ——
> 只收极端样本会把向量的收益算得过于乐观。

> **标注必须人工完成。** 不能用模型先生成一份「期望文件」，再拿它去评测模型自己的检索 ——
> 那测的是模型与自己的自洽程度，与检索质量无关，而且分数通常还很漂亮。
> 这两个工程各 10 来个文件，标注一次半小时可完成。

### 语义型 query 里混进代码标识符会被判为配置错误

加载器（`RagEvalSetLoader`）对 **SEMANTIC** 用例额外校验：query 里不得出现
文件名线索（`.vue` / `.js` / …）或驼峰标识符（`localStorage`、`Navbar`），否则直接抛错。

理由与其它校验同源，但更隐蔽：**一条语义型用例只要写了文件名，它就退化成关键词题，
却仍然被算进语义型的分母** —— 语义型召回率被抬高、向量的增量收益被抹平，
而报告里看不出任何异常。配置写错会让指标变成 0，谁都看得见；这个是让指标悄悄变好。

点名型**不受**此规则约束（写文件名正是它的本分），这条边界有单测守着。

## 四、怎么跑

在**真实运行环境**下（IDEA 里启动，环境变量 `LLM_BASE_URL` / `LLM_API_KEY` 已注入）：

```
GET  /rag-eval/set                 先看一眼用例与期望文件，标注写错的话后面全是白跑
POST /rag-eval/run?ablation=true   跑三组权重消融（默认）
POST /rag-eval/run?ablation=false  只跑线上生效的那组权重，省 2/3 调用
```

跑完报告同时返回并打进日志，形如：

```
┌─ 代码检索召回评测 ────────────────────────────────────────────
│ 评测集：代码检索召回评测集 v1.1，用例 28 条
│ 参数：topK=8，单文件片段上限=3
│ 索引：云雾山旅游站(N 片段) 潮玩手办馆(N 片段) ，耗时 N ms
│ 向量：可用
└───────────────────────────────────────────────────────────────

【总体对照】同一批索引与查询，差异只来自权重
  配置              Recall@8   Precision@8  MRR     命中率
  仅关键词(0/1)     ...
  仅向量(1/0)       ...
  混合              ...
  ⚠ Precision@K 在「每条用例只有 1 个期望文件」时恒等于 1 ÷ 返回文件数，……

【分组对照】点名型靠文件名即可命中，语义型才是向量该发力的地方
  配置              分组      Recall@8   MRR      Top-1
  混合              点名型      ...       ...       ...
  混合              语义型      ...       ...       ...

【向量是否真的参与打分】
  混合              链路检查：28/28 条用例的 top-1 片段向量分 > 0（=0 说明向量根本没进排序）
                    强证据：N/28 条用例的 top-1 关键词分为 0 —— 这些用例的首位排名只能来自向量

【漏召清单】…
  混合              漏召 N 条：…

【排后清单】…
  混合              排后 N 条，榜首占位：<文件>×N、…
```

> 上面这张是**格式示例**，数字与文件名一律留成 `...` / `N`：
> 真实数字每隔一轮就会变，写死在这里的迟早变成又一份过期口径。
> 连「索引耗时」也一样 —— 首轮的 14937 ms 到了第二轮就变成 213 ms（增量索引生效）。

## 五、怎么读结果（按这个顺序）

1. **先看索引片段数**。有任何一个应用是 0，后面所有指标必然是 0 —— 这是链路问题不是算法问题。
2. **再看「向量」那行**。`不可用` 说明 embedding 凭证有问题，此时全部指标退化为纯关键词，
   而「仅关键词」恰好也是消融里的一组，两者会混为一谈。
3. **再看「向量是否真的参与打分」的第二行** —— 但**只有混合组的那两行有意义**：
   - 「仅关键词」组整块显示「不适用」：它的向量分算得出来，只是权重为 0、没进总分，
     照常印「N/N 条向量分 > 0」会让人以为向量参与了排序 —— 而那恰恰是唯一没参与的一组；
   - 「仅向量」组的第二行也显示「不适用」：该组关键词权重为 0，榜首**全部**由向量决定，
     统计出其中几条反而会暗示其余是关键词顶上来的；
   - 混合组里，第一行（向量分 > 0）只是链路检查，向量可用时它必然等于用例总数，不构成证据；
     **第二行（top-1 关键词分为 0 的条数）才是证据** —— 这些用例的首位不可能是关键词推上去的。
     若这个数长期为 0，说明榜首全是字面命中拿下的，向量在这批数据上可以说不存在。

   顺着往下看【漏召清单】与【排后清单】。两者必须分开看，因为**要采取的行动不一样**：
   - **漏召** = 期望文件没进 Top-K，按配置列出**用例号** —— 回答「这一条到底是谁不行」，
     只给百分比看不出是哪几条在拖后腿；
   - **排后** = 期望文件进了 Top-K 但没排首位，按配置汇总**榜首被哪个文件占走** ——
     回答「该治哪个文件」。若榜首长期是同一两个「对谁都像」的文件
     （全局样式 / 首页 / 关于页），那是通用文件淹没，**该治的是它，不是继续调权重**。
     按占位文件汇总而不是列用例号，正是因为要修的是那个文件而不是这批用例。
4. **最后看分组对照**，重点是**语义型那一列**：
   - 若「仅关键词」在语义型上已经很高，说明这批查询的词面与代码重合度高，
     该补的是更「不像代码」的查询，而不是宣布向量无用；
   - 若「仅向量」在点名型上很差，说明 `FILE_MENTION_BONUS` 确实在起作用；
   - 「混合」应当在两类上都不差于任一单路，否则权重需要调整；
   - **语义型的短板通常不在 Recall 而在 MRR/Top-1**：捞到了但排在第三、第四位。
     Top-K 够大时这不影响最终结果（片段照样进上下文），但它决定了
     「将来要不要为省 token 把 topK 调小」。

## 六、成本

| 阶段 | 调用次数（约） |
|---|---|
| 建索引（两个工程，首次） | 10 次（约 23 个文件切出数十个片段，`batch-size=10` 分批） |
| 每条用例检索一次 | 1 次 |
| 全量消融 28 条 × 3 组 | 84 次 |
| **合计** | **约 94 次** |

⚠️ **`app.budget.max-calls` 必须大于这个量级**。闸门耗尽时每条用例都返回空列表，
表现在报告里是「召回率突然全线归零」，很容易被误读成「检索退化了」。

增量索引会大幅降低重复跑的成本：文件没变时 `fileHash` 比对通过，不会重新向量化。

## 七、已知边界

- **`max-chunks-per-file=3` 会压缩 Top-K 的文件覆盖数**。一条需求的期望文件超过 3 个时，
  可能因为配额而永远召不全 —— 这不是检索算法的问题。标注时单条需求建议不超过 3 个期望文件。
- **语义型查询难以完全避开词面重合**。即便刻意用同义改写，「留言」「分类」这类词仍可能
  出现在代码里，关键词路径依然能命中。这是真实的分布，不做人为美化 ——
  它恰好量化了「关键词能白拿多少分」。
- **点名型用例在 `topK ≥ 工程文件数` 时没有鉴别力**。`topK=8`，两个工程各 10 来个文件，
  于是期望文件不论排第几都会进结果 ⇒ 三组（含仅关键词）一律 100% / MRR 1.000 / Top-1 8-8。
  这不是「关键词够用」的证据，是**任务太简单**的证据。要靠它测出点名加成的价值，
  必须让需求里出现相似竞争文件（同一需求同时提到 `Products.vue` 与 `ProductCard.vue`）。
- **「内容在数据文件、改动在展示文件」的需求会被系统性误召**。用例 16 三组全漏即是此例
  （见第十节结论四）：改动落在 `Detail.vue`，但尺寸数据在 `products.js`，
  且后者相关片段密度更高。这类需求本身有歧义，标注与评估都要单独确认。
- **评测会改写全局权重配置**。`RagEvalRunner` 在 `finally` 里还原，
  但若进程在还原前被杀，重启前线上的权重视为被改动过。
- **评测结果不落库**。这是实验数据不是运营数据，跨批次比较靠记录报告即可。

## 八、首轮实测：一次被缺陷抬高的成绩（2026-09-23）

第一次真跑（`ablation=false`，即只跑线上权重）拿到的心脏数字：

| 配置 | Recall@8 | Precision@8 | MRR | 命中率 | 点名型 Recall@8 | 语义型 Recall@8 |
|---|---|---|---|---|---|---|
| 混合 0.7/0.3 | 93.8%（15/16） | 21.4% | 0.786 | 93.8% | 100%（8/8） | 87.5%（7/8） |

从逐条明细再算出来的两个数：**Top-1 = 11/16（68.8%）**；
**点名型 MRR 0.938，语义型 MRR 0.635** —— 语义型 8 条里只有 4 条排首位。

### 这一轮不能作为基线：点名加成退化成「按扩展名批发」

**症状**：「点名型 8/8」好得可疑，而用例 01 更矛盾 —— 需求点名了 `Navbar.vue`，
排第一的却是 `Attractions.vue`。

**定位方式（可复用）**：`QueryTerms` 是纯函数、不依赖 Spring 与网络，
可以直接 `javac` 出项目源码 + 一个探针类，把 16 条用例的术语、加分判定、
关键词分全部离线复算一遍，再与线上报告对照。复算结果：

| 用例 | 术语里出现的扩展名词 | 「被点名」的文件数 | 全工程 .vue 文件数 |
|---|---|---|---|
| tour 的 4 条点名型 | `vue`（来自 `Navbar.vue` 等） | 8/14 | 8 |
| shop 的 4 条点名型 | `vue`；`products.js` 那条另含 `products` | 8~9/15 | 8 |

**根因有两处，同一个主题：把扩展名当成了标识符。**

1. `QueryTerms#extract` 会把 `Navbar.vue` 切成 `navbar` **和** `vue`；
2. `mentionsFile` 判定「被点名」用的是 `路径.contains(术语)`，
   于是 `vue` 命中**每一条** .vue 路径 —— 全工程 .vue 文件各得 `FILE_MENTION_BONUS = 0.5`。
   这个加成大于一整份加权得分（0..1）的一半，拿到就绝对领先，
   净效果成了「.vue 文件整体排在 .js/.css/.html 之前」。
   `products.js` 那条同理：驼峰拆出的 `product` 命中了 `products.js` 与 `Products.vue`。

**为什么这会毁掉指标**：加成对期望文件和它的竞争者同等生效 ⇒ 净差分为零，
「点名型 100%」根本不是加成的功劳，而是「所有 .vue 都被加分 + topK=8 ≥ 工程里的 .vue 文件数」
的必然结果。这一列的 100% 没有鉴别力。

**修法**（`QueryTerms`，2026-09-23）：扩展名词从术语里剔除（只剩扩展名时退回原集合，
否则术语集为空会让检索器直接放弃检索）；`mentionsFile` 改为
**「术语与文件名主干归一化后相等」**（大小写与 `-`/`_` 不参与比较），
不再做路径子串匹配 —— 目录名（`views`）与部分名（`product` 对 `products`）都不算点名。

**预期**：修复后重跑，点名型的分数**会下降**，那才是正常值。
修复前后的两轮口径不同，不可直接比较。

### 另外三条读法修正（已落进报告与本文档）

1. `Precision@8` 在该标注集下恒等于 `1 ÷ 返回文件数`（21.4% 与逐条吻合），与检索质量无关；
   `命中率` 恒等于 `Recall@K`。报告里已加脚注。
2. 「向量是否参与打分」的旧证据（top-1 向量分 > 0）是必然成立的 —— 换成
   **top-1 关键词分为 0 的条数**。首轮实测该值为 **2/16（用例 05、13）**，
   这两条的首位排名只能来自向量。
3. **语义型的短板在排名，不在召回**：掉到第 3、4 位的两条，top-1 是
   `src/styles/main.css` 与 `index.html` 这类「通用文件」——
   它们对任何查询都有不低的余弦相似度。这是向量检索的典型病（通用文件淹没），
   值得后续验证的方向是给「全局样式 / 入口文件」加路径先验或长度归一，
   而不是继续调权重。**但样本只有 16 条，先不要为它改算法。**

## 九、第二轮实测：三组权重消融（2026-09-23）

修复后重跑 `POST /rag-eval/run`（默认 `ablation=true`），第一次拿到三组对照。

| 配置 | Recall@8 | MRR | 命中率 | 点名型 Recall / MRR / Top-1 | 语义型 Recall / MRR / Top-1 |
|---|---|---|---|---|---|
| 仅关键词(0/1) | 75.0%（12/16） | 0.750 | 75.0% | 100% / 1.000 / 8-8 | **50.0%** / 0.500 / 4-8 |
| 仅向量(1/0) | 93.8%（15/16） | 0.786 | 93.8% | 100% / 1.000 / 8-8 | **87.5%** / 0.573 / 3-8 |
| 混合(0.7/0.3) | 93.8%（15/16） | 0.818 | 93.8% | 100% / 1.000 / 8-8 | **87.5%** / 0.635 / 4-8 |

### 修复生效了吗：生效了，但痕迹只在排名上

上轮预期「修复后点名型分数**会下降**」，实测 Recall **没有下降**。原因是
`topK=8` 已经覆盖工程里全部 .vue 文件，期望文件无论排第几都会出现在结果里
⇒ **Recall 对这一缺陷不敏感**。缺陷的唯一痕迹是**排名**：

- 用例 01 的榜首从 `src/pages/Attractions.vue`（与本需求无关）回到期望的 `Navbar.vue`；
- 点名型 MRR `0.938 → 1.000`、Top-1 `7/8 → 8/8`。

这也顺带证明上轮「给分组补 MRR 与 Top-1」是必要的 —— 只看 Recall，这轮会被读成「修复没效果」。

### 结论一：向量是必要的 —— 唯一一个量级可信的效应

**语义型 Recall：仅关键词 50.0%（4/8）→ 仅向量 87.5%（7/8），+37.5 个百分点 / 多召回 3 条。**
16 条用例里有 8 条只描述功能、不含任何代码标识符，纯关键词只能捞到其中一半。
这就是「为什么要有向量」的直接答案，也是整套消融里唯一一个远超噪声的差异。

### 结论二：混合取了两者的长处，且不劣于任一单路

语义型上，混合的 **Recall 87.5% 追平仅向量**，**Top-1 4/8 追平仅关键词**（且高于仅向量的 3/8）。
换句话讲，0.3 的关键词权重干了它该干的事：**召回广度交给向量，榜首位置由关键词校准**。

单看「仅向量」那一列还能看到病根：召回 87.5% 却 Top-1 只有 37.5% ——
纯语义向量容易把 `main.css`、`index.html` 这类「对谁都像」的通用文件排到前面，
关键词分把它们压了下去。这正是关键词权重在一套以向量为主的方案里仍然值得保留的理由。

### 结论三：不要把 MRR 的组间差当成证据（n=16 下它是噪声）

| 对比 | MRR 差 | 折算成「用例前进一名」 |
|---|---|---|
| 混合 0.818 vs 仅向量 0.786 | 0.032 | ≈ 1 条 |
| 混合 0.818 vs 仅关键词 0.750 | 0.068 | ≈ 2 条 |
| 混合语义型 0.635 vs 仅向量 0.573 | 0.062 | ≈ 1 条 |

MRR 是 16 条（分组仅 8 条）的平均，`0.032 × 16 ≈ 0.5`，恰好等于
**一条用例从第 2 名前进到第 1 名**。这个量级在 8~16 条样本上就是噪声。
**能站住的只有结论一那个 +37.5pp。**

### 结论四：点名型这一列已经饱和，没有鉴别力

三组（**含「仅关键词」**）全部是 100% / MRR 1.000 / Top-1 8-8。
这意味着点名型用例连关键词单路都能满分，它**无法支撑**「`FILE_MENTION_BONUS` 有用」
或「关键词权重 0.3 有用」这类结论。上轮的 100% 是缺陷的产物，
这一轮的 100% 是任务太简单的产物 —— 成因不同，结果一样：这一列测不出东西。

### 所以：权重不调，该改的是标注集

现有数据支持「保留向量高权重 + 保留一路关键词」，**不支持**「0.7 / 0.3 是最优」。
要回答后者，得先让标注集有分辨力：

1. **点名型加干扰项**。现在的点名型查询里，文件名主干（`navbar`、`productcard`…）
   在工程内是独一无二的词，一次命中就到底。要测出加成是否会把**错的那个**顶上去，
   得让用例里出现相似竞争者（同时提到 `Products.vue` 与 `ProductCard.vue`，
   或利用两个工程各有一个的 `Navbar.vue` / `NavBar.vue`）。
2. **补「多期望文件」的用例**（如「导航栏和页脚一起改」）。现在清一色单个期望文件，
   导致 `Precision@K` 与 `命中率` 双双退化（见第二节）。多期望文件才能让它们恢复含义。
3. **语义型从 8 条扩到 20 条以上**。分组样本 8 条时，MRR 的组间差异整个落在噪声量级；
   样本上去之前，任何「微调权重」的结论都是拟合噪声。

### 已执行：语义型扩到 20 条（v1.0 → v1.1）

上表第 3 条已落地 —— 标注集升到 **v1.1，28 条（点名 8 + 语义 20）**，

**仍未做**：点名型加干扰项、补多期望文件用例（上表 1、2 条）——

## 十一、横切文件折扣：做了，但默认关闭（2026-09-23）

### 动它之前先修正一个前提：排后不产生漏召

上一节说「该做的是通用文件那一项」，验收方式是看榜首占位是否下降。
真去实现前先把这批数据重看了一遍，发现一个更要紧的事实：

**混合组每条用例返回 4~7 个文件，Top-K 片段位（8）基本没被占满，
而且除用例 16 那条独立漏召外，期望文件全都在结果里。**

也就是说：**排后 ≠ 漏召**。`main.css` 抢走首位，并没有把期望文件挤出上下文 ——
它占的是**字符预算与模型注意力**，不是正确文件的位置。
工程文件数远小于 `topK` 时，这个代价接近于零。

⇒ 这项改动是**预防性的**（工程变大、文件数逼近 Top-K 时才真正伤到交付），
不是当前缺陷的修复。定位不同，做法就不同：**它不该有「看起来更聪明」的默认值。**

### 实现：横切文件在向量分上打折

- `QueryTerms#isGenericFile` —— 判据只有两条**结构性规则**，没有任何本工程特有的文件名：
  1. **全局样式扩展名**：`css / scss / sass / less / styl`（影响整站外观，任何界面需求都沾边）；
  2. **框架约定入口名**：主干 ∈ `main / index / app`，且扩展名 ∈
     `js / ts / jsx / tsx / mjs / cjs / html / htm / vue` ——
     `main.js`、`App.vue`、`index.html` 是任何 Vue 工程都有的入口，按它们降权不属于「为某个工程调参」。
     限定扩展名是必须的：否则 `docs/index.md` 这种同名文件也会被算成入口。
- `QueryTerms#genericFilePenalty(terms, filePath, configured)` —— 返回应乘在**向量分**上的系数。
  **只削向量分**：关键词分是「字面对得上」的硬信号（路径 1.0 / 标识符 0.85 / 正文 0.4），
  它跟「这个文件是否泛化」无关；点名加成更是明确指令，绝不能碰。
- `RagProperties#genericFilePenalty` 默认 **1.0**，取值 ≤0 或 ≥1（含 `NaN`）都归一为 1.0。

### 为什么默认关闭：折扣的代价是即时可见的

`tour-font-semantic-17`（「网站的默认字体加载太慢了，想换成系统自带的那种」）
期望文件**正是 `src/styles/main.css`**，而且需求里**不含文件名** ⇒ 拿不到点名豁免。
打折后它可能直接掉出 Top-K，**一条命中会变成漏召**。

所以这不是「装上就该用」的开关，而是必须实测对比才敢打开的旋钮：

```yaml
app:
  rag:
    generic-file-penalty: 0.9   # 默认 1.0（关闭）；建议区间 0.85 ~ 0.95
```

改完重跑 `POST /rag-eval/run`，**两个清单一起看**：

| 观察项 | 期望 | 只看它的后果 |
|---|---|---|
| 【排后清单】榜首占位 | 下降 | 只盯这个，会把「把正确文件也压下去了」当成成功 |
| 【漏召清单】条数 | 不增加 | 若变长，说明折扣压过了它该保护的召回 |

### 一个必须说清的边界：它只治得了一半

排后的 8 条里，占位者是 `main.css`（4 次）与 `About.vue`（3 次）。
折扣**只覆盖前者** —— `About.vue` 既不是样式也不是框架入口，不在判据内。

`About.vue` 的问题性质不同：它不是「横切」，而是**整页泛化中文文案，与任何中文需求都泛泛相关**。
用结构规则表达不了「这个文件内容太泛」；要治得引入**内容判别力度量**
（如片段内业务标识符密度），那是另一个方向、且更容易过拟合，本轮不做。

⇒ 启用后如果【排后清单】里的 `main.css` 归零、`About.vue` 照旧，那是**预期结果**，不是没生效。

### 反向验证三路（各自单独跑）

| 回退方向 | 结果 |
|---|---|
| 摘掉点名豁免（`mentionsFile` → `false`） | 恰好红 `mentionedFileIsExempt` |
| 摘掉配置开关守卫（`if (false)`） | 恰好红 `disabledByDefault` |
| 去掉入口判据的扩展名限定 | 恰好红 `frameworkEntryNamesAreGeneric`（`docs/index.md` 被判成入口） |

三路都是干净的断言失败（`Failures: 1, Errors: 0`），没有编译错或越界这类假信号。均已还原。

全量 **503 通过 / 0 失败 / 2 skipped**（494 → 503，+9 例：`QueryTermsTest` +6、`RagPropertiesTest` +3）。
