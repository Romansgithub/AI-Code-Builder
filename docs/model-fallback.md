# 多模型降级

## 为什么需要它

单一模型配置下，模型服务的**任何一次抖动都直接等于用户看到失败**：
限流、5xx、网络超时都会让整次生成白费 —— 而且已经烧掉的 token 不会退。

更麻烦的是额度耗尽：所有请求会**稳定失败**，直到人工换 key。
对开发联调来说，这等于「项目突然不能用了」。

多模型降级让这类失败从「直接报错」变成「自动换一个继续」。

## 配置

```yaml
app:
  model-fallback:
    enabled: ${APP_MODEL_FALLBACK_ENABLED:true}
    attempts-per-candidate: ${APP_MODEL_FALLBACK_ATTEMPTS:1}
    notify-user: ${APP_MODEL_FALLBACK_NOTIFY:true}
    candidates: []
```

**默认 `candidates: []`（空）** —— 行为与改造前完全一致，不引入任何新失败面。
降级是「显式开启」的能力。

### 候选字段

全部可选，未填的字段沿用主模型配置：

| 字段 | 说明 |
|---|---|
| `model-name` | **必填**。为空则该候选被跳过 |
| `base-url` | 覆盖 base-url，用于跨服务商 |
| `api-key` | 覆盖 key，用于跨账号 |
| `max-tokens` | 覆盖输出上限 |
| `label` | 日志与前端提示用的可读名 |

### 两种典型配法

**① 换模型档位**（同名不同档，成本更低）：

```yaml
candidates:
  - model-name: qwen-turbo
    label: 通义千问（经济档）
  - model-name: qwen-plus
    api-key: ${LLM_API_KEY_BACKUP:}
    label: 通义千问（备用账号）
```

**② 换 key**（应对单 key 额度耗尽 —— 开发者最常遇到的场景）：

```yaml
candidates:
  - model-name: qwen-plus
    api-key: ${LLM_API_KEY_BACKUP}
    label: 备用账号
```

> 把「换 key」表达成候选链上的一个节点，比单独开一套 key 轮换逻辑简单得多。

## 什么失败才降级

**只对「换个模型 / 换个 key 可能就好了」的失败降级。**

| 降级 | 不降级 |
|---|---|
| 限流 429 | 请求参数非法 |
| 5xx 服务端错误 | 上下文超长 |
| 超时 | 内容被安全策略拦截 |
| 鉴权失败 401/403（额度耗尽） | 其它未识别异常 |
| 模型不存在 404 | |
| 网络不可达 / DNS 失败 | |

无脑降级看起来更「稳」，实际有害：参数非法、内容拦截这类问题换任何模型
都是同样结果，重试只是多烧一次调用、多让用户等一轮，最后还是失败。

这与构建自愈里「只对代码问题重试、环境问题不重试」是同一条原则：
**重试之前先问「重试能让它变好吗」**。

### ⚠️ 与 LangChain4j 自带分类的关键区别

LangChain4j 有 `RetriableException` / `NonRetriableException` 两族异常，
**看起来可以直接拿来判断，但语义并不相同**：

| | 回答的问题 |
|---|---|
| LangChain4j 的分类 | 「重试**同一个模型**有意义吗」 |
| 我们的判断 | 「换个模型或**换个 key** 有意义吗」 |

这个差异在 `AuthenticationException` 上最清楚：它继承
`NonRetriableException`（重试同一个 key 当然没用），但对我们恰恰是
**最该降级的场景之一** —— 换个 key 就解决了，而额度耗尽通常正是这样返回的。

`ModelNotFoundException` 同理：当前模型名可能写错，换候选完全可能正常。

**因此不直接复用 LangChain4j 的判断，而是按自己的语义重新分类。**
`FallbackFailureClassifierTest.authentication()` 专门锁死这一点。

## 两条关键约束

### ① 一旦开始输出，就不能再降级

流式响应是**不可回滚**的。如果主模型已经吐了 500 个 token 之后才失败，
再切备用模型重新生成，用户拿到的会是「前 500 token + 备用模型的完整输出」
—— **比直接报错更糟，因为它是静默的**，用户会以为生成成功了。

所以规则是：**只在「尚未收到任何 partial response」时才能降级**。
一旦有 token 流出，后续失败一律如实上报。

这与 HTTP 语义一致：响应头已发出就无法再改状态码。

> 每个候选独占一个「是否已输出」标志。若跨候选复用，会出现
> 「主模型吐过 token → 备用模型误以为也不能降级」的错误判断
> （`producedFlagShouldNotLeakAcrossCandidates` 锁死这条）。

### ② 同步抛异常也要接住

有些实现会同步 `throw` 而不是回调 `onError`。两条路径都要接住，
否则降级在这种实现上会**静默失效**。

## 用户可见性

降级发生时会通过 SSE 进度事件告知用户：

```
模型服务异常（模型服务限流），已自动切换到备用模型 通义千问（经济档）
```

**为什么明说而不是静默**：备用模型往往档位更低，输出质量可能与预期不同。
静默降级会让用户困惑于「为什么这次生成得不一样」，甚至误判为模型变笨了。
明说既是知情权，也是排查线索。

配置 `notify-user: false` 可关闭。

## 实现

- `FallbackFailureClassifier` —— 判断该不该降级（纯函数，易测）
- `FallbackStreamingChatModel` —— 装饰器，按链逐个尝试
- `FallbackModelProvider` —— 按配置装配候选链
- 装配点：`AiCodeGeneratorServiceFactory.createAiCodeGeneratorService`

主模型排在候选队列第 0 位，逻辑上与其他候选完全一致 ——
「主模型」与「备用模型」的区别只是顺序，不需要两套代码路径。

**未配置候选时返回原模型对象**，不做任何包装 ——
少一层包装就少一份排查时的迷惑。

## 与调用预算的关系

两者互补，都为了「别让一次生成白费」：

| | 预算闸门 | 多模型降级 |
|---|---|---|
| 作用 | 防止无节制消耗 | 单点故障时不放弃 |
| 时机 | 调用**前**（拦截） | 调用**失败后**（补救） |
| 报错方式 | 明确拒绝并说明原因 | 自动切换，仅提示 |

注意降级会**额外消耗预算**（每次尝试都算一次调用）。
`attempts-per-candidate` 设大时尤其明显 —— 真正故障时等待时间也会翻倍。

## 已知限制

- **降级不解决「两边都没额度」**。候选链全部失败时如实上报，
  不会无限尝试。
- **只覆盖流式生成模型**。路由用的同步 `ChatModel` 未接入降级
  （它的失败会让创建应用失败，但额度消耗极小）。
- **候选链在启动时确定**，运行时不可动态增减。
- **不做熔断**：某一个候选持续失败时，每个请求都会先撞上它再降级，
  多花一次调用。真正的生产系统需要加熔断器（如 Resilience4j），
  这里刻意不做 —— 本项目是单实例开发规模，加熔断会让代码复杂度
  远超收益。这是**已知的、有意接受**的简化。
