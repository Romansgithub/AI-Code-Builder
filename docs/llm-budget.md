# LLM 调用预算（防额度烧光）

## 为什么需要它

这个项目里有四条会**真实消耗额度**的路径，彼此不知道对方花了多少：

| 路径 | 入口 | 一次消耗 |
|---|---|---|
| 代码生成 | `POST /app/chat/gen/code` | 1 次 |
| 类型路由 | `POST /app/add`（创建应用时判定 `html`/`vue_project`/`multi_file`） | 1 次 |
| 构建自愈 | 生成后构建失败自动触发 | 最多 `max-attempts` 次（默认 2） |
| 评测跑批 | `POST /eval/run` | 每用例 1 次 + 各自的自愈次数 |

单次都不算贵，但都不受约束。开发联调时随手多点几次生成、或者开一轮评测
（8 条用例 × 每条最多 3 次生成 = 最坏 24 次完整生成），免费额度就见底了
——**而且过程中没有任何提示**，等你发现时已经用不了了。

## 设计取舍：为什么用「次数」而不是「token」

| | 调用次数 | token 数 |
|---|---|---|
| 何时可知 | 发起**前** | 响应结束后 |
| 能否拦截 | ✅ 能 | ❌ 只能事后审计 |

token 数只有在响应结束（流式响应还要完全读完）才知道，等发现超了，钱已经花出去了。
次数在发起前就能判定，可以真正拦住下一次调用。

两者的关系是：**次数是闸门（事前，能拦），token 是仪表盘（事后，能看）**。
本项目优先做闸门；`max-tokens` 配置控制的是单次成本天花板，是另一根杠杆。

## 配置

```yaml
app:
  budget:
    enabled: ${APP_BUDGET_ENABLED:true}          # 总开关，false = 不限制
    max-calls: ${APP_BUDGET_MAX_CALLS:200}       # 进程内调用次数上限
    warn-ratio: ${APP_BUDGET_WARN_RATIO:0.8}     # 用量到 80% 时打一次警告
    reject-when-exhausted: ${APP_BUDGET_REJECT:true}  # 触顶后拒绝（false = 只告警）
```

**默认开启**。一个「默认关闭」的预算等于没有预算 ——
它会重蹈 `app.eval.enabled` 曾被误写成 `true` 的覆辙（那个是反向错误，
但同样是「默认值与注释意图不符」）。

### 环境变量速查

| 场景 | 设置 |
|---|---|
| 想完全关掉限制 | `APP_BUDGET_ENABLED=false` |
| 想跑一轮评测 | `APP_BUDGET_MAX_CALLS=500`（或临时关掉） |
| 只想观测不拦截 | `APP_BUDGET_REJECT=false` |

## 使用

### 查看用量

```bash
GET /api/budget/usage        # 需管理员登录
```

返回已用 / 剩余 / 被拦截次数 / 已用百分比。

### 重置计数（不重启服务）

```bash
POST /api/budget/reset       # 需管理员登录
```

存在的理由很实际：额度用完时重启服务要重新登录、重新开应用，
代价比按需重置大得多。

⚠️ **重置是全局的** —— 重置整个进程的计数，不只是当前用户。
这在单实例、开发者自用的场景下是合理简化。

## 实现要点

### 计数点必须是唯一交汇处

计数一旦分散，必然出现「新增一条调用路径但忘了计数」的漏洞 ——
而这类漏洞**不会报错，只会静默漏账**。所以闸门装在：

- `AiCodeGeneratorFacade.generateCodeStream` —— 用户生成 + 评测跑批的**唯一**交汇点
- `BuildSelfHealingService.askAiToFix` —— 自愈**直接调 service，不经过 Facade**，必须单独装
- `AppServiceImpl.createApp` —— 路由是独立路径，不经过 Facade

> 自愈这一点特别容易漏：它一次生成失败最多触发 2 轮完整生成，
> 是**最贵**的路径。漏掉它的后果是「预算显示没用到，实际已经花了几倍」。

### 一次生成恰好记一次

用户生成这条路径上，`AppServiceImpl` 与 `Facade` 都会碰到预算。
为避免重复计数，两者用的是**不同方法**：

- `AppServiceImpl` 用 `assertAvailable()` —— **只检查，不消耗**
- `Facade` 用 `acquire()` —— 检查并落账

顺序是「抢占任务 → 探预算 → 真正调用（记账）」。这样：
- 被幂等保护转为「订阅」的请求**不会**被算成一次调用（它根本不调模型）
- 额度不足时，任务现场会被 `finishTask()` 归还，不会留下
  「已注册但从未启动」的 RUNNING 任务把应用卡住

> 若顺序反了（先记账再判断要不要跑），账目会虚高；
> 若不做探路检查就直接抢占任务，额度不足会留下僵尸任务，
> 应用被幂等保护挡住直到看门狗超时（默认 20 分钟）。

### 自愈遇到预算耗尽必须中止循环，不能当作「没修好」

`askAiToFix` 原本返回 `boolean`，且吞掉所有异常返回 `false` ——
而 `false` 在外层循环的语义是「继续下一轮」。

若预算异常被吞成 `false`，后续每一轮都会因额度耗尽而失败，
等于把剩余重试次数在一次**热循环**里空转烧完：用户看到「一直在修复」，
但什么都没发生。因此改为三态：

```java
private enum AiFixOutcome {
    REPAIRED,          // 完成了修复动作，去重新构建验证
    NOT_REPAIRED,      // 这轮没修好，可以再试
    BUDGET_EXHAUSTED   // 没资格再试 —— 必须中止循环
}
```

### 并发安全

调用发生在多个虚拟线程上（生成在 `gen-task-*`，自愈可能在其他线程），
所以用 `AtomicLong` 做 CAS 自增。

- 不用 `synchronized`：每次只是一个 CAS，竞争极低，不需要锁开销
- 不用 `LongAdder`：它适合高频写低频读，这里读写频率相当，
  且需要「读到精确值」做阈值判断

被拒绝的调用会 `decrementAndGet()` 把不该记的账退回去，
否则计数器虚高，「实际调用数」就不可信了。

## 已知限制

- **计数在进程内，重启即清零**。开发场景合理（重启本就意味着重新开始一轮），
  但它**不是配额系统**。要跨实例、跨重启地限流，需把计数器换成 Redis。
- **按次不按 token**。一次生成长度差异很大，次数的成本估算精度有限
  （所以配置里同时收紧了 `max-tokens`）。
- **`assertAvailable` 与 `acquire` 之间有理论竞态**：检查通过、落账时已被抢光。
  此时 `acquire` 仍会正常抛异常，只是准备工作白做一次 ——
  相比「账目虚高一倍」，这个代价更可接受。
