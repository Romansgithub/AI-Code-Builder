# 设计说明

`eval.md`、`llm-budget.md`、`model-fallback.md`、`rag-eval.md` 四篇只写怎么用。
这里放它们背后的动机、取舍与踩过的坑，以及检索评测的历次实验记录。

## 一、AI 输出可评测性

### 动机

改了自愈提示词、换了模型、调了重试轮数之后，效果是变好还是变差？没有固定评测集时只能靠感觉，说不清楚。有了它，跑一轮就能对比指标。

### 自愈成功率 0% 与「自愈没上场」是两件事

- 成功率 0%：触发了自愈但全失败，自愈有问题。
- `healingUsedCount = 0`：压根没有用例触发自愈，通常是因为一次通过率很高。

接口在 `healingUsedCount = 0` 时返回 `null` 而不是 `0`，就是为了避免把后者误读成前者。

### 通过率的分母不含故障注入用例

配置了故障注入的用例不进通过率的分子分母。它的首轮失败是设计目的，靠注入制造一次必然失败给自愈出题，计进去等于用一次刻意的失败去拉低头条指标，报告读起来像生成质量变差了。

所以分母是「用例总数 − 故障注入用例数」。当前评测集 9 条里有 1 条注入用例，分母就是 8。看到 `8/8` 不是写错了，那 1 条被刻意排除，它只进自愈成功率的分母。

对外材料里如果同时写「9 条用例」和「8/8 通过率」，要交代 9 = 8 条常规 + 1 条注入，否则读者会以为两个数字对不上。

### prompt 为什么必须写死

同一 prompt 才能跨批次比较。跑批因此刻意不走 AI 路由：路由由模型决定，同一段 prompt 可能这次判成 HTML、下次判成 Vue，指标就失去可比性。

### 改评测集为什么必须升 version

用例增删改之后不升版本，跨批次对比就是在拿两套不同的考卷比分数，`EvalSetLoader` 因此强制校验 `version` 非空。

加载时还会校验用例非空、id 唯一且安全、类型可识别、prompt 非空，任一不满足直接抛错并指出是哪条用例。错误指标比没有指标更危险，因为前者看起来可信。

### 隔离性

| 关注点 | 做法 |
|---|---|
| 产物隔离 | 写在 `code-output-dir/eval-run/` 下，不混进用户应用列表 |
| 残留污染 | 每条用例开跑前清空自己的目录，否则「这轮通过了」可能是上轮的 dist 还在 |
| 会话隔离 | 用负数 `appId` 作评测会话，与真实应用 id 空间天然隔开 |
| 成本控制 | 默认关闭，手动开启 |
| 主流程保护 | 采集与上报各兜一层异常，埋点失败不影响用户拿到代码 |

### 埋点为什么放在 AiCodeGeneratorFacade

它是唯一能同时拿到生成耗时与构建耗时的时间线切点。Vue 分支的埋点放在 `finally`，因为异常路径恰恰是最需要被统计的样本。

## 二、LLM 调用预算

### 动机

项目里有四条真实消耗额度的路径，彼此不知道对方花了多少：

| 路径 | 入口 | 一次消耗 |
|---|---|---|
| 代码生成 | `POST /app/chat/gen/code` | 1 次 |
| 类型路由 | `POST /app/add` | 1 次 |
| 构建自愈 | 生成后构建失败自动触发 | 最多 `max-attempts` 次（默认 2） |
| 评测跑批 | `POST /eval/run` | 每用例 1 次 + 各自的自愈次数 |

单次都不算贵，但都不受约束。开发联调时多点几次生成，或者开一轮评测（8 条用例 × 每条最多 3 次生成 = 最坏 24 次完整生成），免费额度就见底了，过程中没有任何提示。

### 为什么按次数而不是按 token

| | 调用次数 | token 数 |
|---|---|---|
| 何时可知 | 发起前 | 响应结束后 |
| 能否拦截 | 能 | 只能事后审计 |

token 数只有在响应结束（流式响应还要完全读完）才知道，等发现超了钱已经花出去了。次数在发起前就能判定，可以真正拦住下一次调用。

次数是闸门，事前能拦；token 是仪表盘，事后能看。本项目优先做闸门，`max-tokens` 控制的是单次成本天花板，是另一根杠杆。

### 为什么默认开启

一个默认关闭的预算等于没有预算。它会重蹈 `app.eval.enabled` 曾被误写成 `true` 的覆辙，那个是反向错误，但同样是默认值与注释意图不符。

### 计数点为什么必须是唯一交汇处

计数一旦分散，必然出现「新增一条调用路径但忘了计数」的漏洞，而这类漏洞不会报错，只会静默漏账。所以闸门装在：

- `AiCodeGeneratorFacade.generateCodeStream`：用户生成与评测跑批的唯一交汇点
- `BuildSelfHealingService.askAiToFix`：自愈直接调 service，不经过 Facade，必须单独装
- `AppServiceImpl.createApp`：路由是独立路径，不经过 Facade

自愈这一点特别容易漏。它一次生成失败最多触发 2 轮完整生成，是最贵的路径；漏掉它的后果是预算显示没用到，实际已经花了几倍。

### 一次生成恰好记一次

用户生成这条路径上，`AppServiceImpl` 与 `Facade` 都会碰到预算。为避免重复计数，两者用的是不同方法：

- `AppServiceImpl` 用 `assertAvailable()`，只检查不消耗
- `Facade` 用 `acquire()`，检查并落账

顺序是「抢占任务 → 探预算 → 真正调用（记账）」，这样有两个好处：被幂等保护转为订阅的请求不会被算成一次调用（它根本不调模型）；额度不足时任务现场会被 `finishTask()` 归还，不会留下已注册但从未启动的 RUNNING 任务把应用卡住。

顺序反了（先记账再判断要不要跑）账目会虚高；不做探路检查就直接抢占任务，额度不足会留下僵尸任务，应用被幂等保护挡住直到看门狗超时（默认 20 分钟）。

### 自愈遇到预算耗尽必须中止循环

`askAiToFix` 原本返回 `boolean`，吞掉所有异常返回 `false`，而 `false` 在外层循环的语义是「继续下一轮」。预算异常被吞成 `false` 后，后续每一轮都会因额度耗尽而失败，等于把剩余重试次数在一次热循环里空转烧完，用户看到「一直在修复」但什么都没发生。因此改成三态：

```java
private enum AiFixOutcome {
    REPAIRED,          // 完成了修复动作，去重新构建验证
    NOT_REPAIRED,      // 这轮没修好，可以再试
    BUDGET_EXHAUSTED   // 没资格再试，必须中止循环
}
```

### 并发用什么

调用发生在多个虚拟线程上（生成在 `gen-task-*`，自愈可能在其他线程），所以用 `AtomicLong` 做 CAS 自增。

不用 `synchronized`：每次只是一个 CAS，竞争极低，不需要锁开销。不用 `LongAdder`：它适合高频写低频读，这里读写频率相当，且需要读到精确值做阈值判断。

被拒绝的调用会 `decrementAndGet()` 把不该记的账退回去，否则计数器虚高，实际调用数就不可信了。

### 重置为什么是全局的

额度用完时重启服务要重新登录、重新开应用，代价比按需重置大得多，这是这个接口存在的理由。重置整个进程的计数而不只是当前用户，在单实例、开发者自用的场景下是合理简化。

## 三、多模型降级

### 动机

单一模型配置下，模型服务的任何一次抖动都直接等于用户看到失败：限流、5xx、网络超时都会让整次生成白费，已经烧掉的 token 也不会退。额度耗尽更麻烦，所有请求会稳定失败直到人工换 key，对开发联调来说等于项目突然不能用了。多模型降级把这类失败从直接报错变成自动换一个继续。

### 为什么默认空候选

行为与改造前完全一致，不引入任何新失败面。降级是要显式开启的能力。

### 只对能靠换模型解决的失败降级

| 降级 | 不降级 |
|---|---|
| 限流 429 | 请求参数非法 |
| 5xx 服务端错误 | 上下文超长 |
| 超时 | 内容被安全策略拦截 |
| 鉴权失败 401/403（额度耗尽） | 其它未识别异常 |
| 模型不存在 404 | |
| 网络不可达 / DNS 失败 | |

无脑降级看起来更稳，实际有害：参数非法、内容拦截这类问题换任何模型都是同样结果，重试只是多烧一次调用、多让用户等一轮，最后还是失败。这与构建自愈里「只对代码问题重试、环境问题不重试」是同一条原则。

### 为什么不直接复用 LangChain4j 的异常分类

LangChain4j 有 `RetriableException` / `NonRetriableException` 两族异常，看起来可以直接拿来判断，但语义不同：

| | 回答的问题 |
|---|---|
| LangChain4j 的分类 | 重试同一个模型有意义吗 |
| 我们的判断 | 换个模型或换个 key 有意义吗 |

差异在 `AuthenticationException` 上最清楚。它继承 `NonRetriableException`（重试同一个 key 当然没用），但对我们恰恰是最该降级的场景之一，换个 key 就解决了，而额度耗尽通常正是这样返回的。`ModelNotFoundException` 同理，当前模型名可能写错，换候选完全可能正常。

所以按自己的语义重新分类，不直接复用。`FallbackFailureClassifierTest.authentication()` 专门锁死这一点。

### 一旦开始输出就不能再降级

流式响应不可回滚。主模型已经吐了 500 个 token 之后才失败，再切备用模型重新生成，用户拿到的会是前 500 token 加上备用模型的完整输出，比直接报错更糟，因为它是静默的，用户会以为生成成功了。

规则是只在尚未收到任何 partial response 时才能降级，一旦有 token 流出，后续失败一律如实上报。这与 HTTP 语义一致：响应头已发出就无法再改状态码。

每个候选独占一个「是否已输出」标志。跨候选复用会出现「主模型吐过 token，备用模型误以为也不能降级」的错误判断，`producedFlagShouldNotLeakAcrossCandidates` 锁死这条。

### 同步抛异常也要接住

有些实现会同步 `throw` 而不是回调 `onError`，两条路径都要接住，否则降级在这种实现上会静默失效。

### 为什么降级要明说

备用模型往往档位更低，输出质量可能与预期不同。静默降级会让用户困惑于「为什么这次生成得不一样」，甚至误判为模型变笨了。明说既是知情权，也是排查线索。

### 主模型排在第 0 位

主模型与其他候选在逻辑上完全一致，「主模型」与「备用模型」的区别只是顺序，不需要两套代码路径。未配置候选时返回原模型对象，不做包装，少一层包装就少一份排查时的迷惑。

### 与调用预算的关系

两者互补，都为了别让一次生成白费：

| | 预算闸门 | 多模型降级 |
|---|---|---|
| 作用 | 防止无节制消耗 | 单点故障时不放弃 |
| 时机 | 调用前（拦截） | 调用失败后（补救） |
| 报错方式 | 明确拒绝并说明原因 | 自动切换，仅提示 |

降级会额外消耗预算，每次尝试都算一次调用，`attempts-per-candidate` 设大时尤其明显，真正故障时等待时间也会翻倍。

## 四、检索召回评测

### 为什么不复用代码生成评测

`POST /eval/run` 拿不到任何 RAG 数据，这是设计使然。评测跑批用的是负数 appId（`EvalScope`），检索链路上有三处闸门会因此直接跳过：

| 位置 | 条件 | 后果 |
|---|---|---|
| `CodeRetriever#retrieve` | `appId <= 0` | 直接返回空列表 |
| `CodeIndexService#indexAfterGeneration` | `appId <= 0 \|\| EvalScope.isActive()` | 不建索引 |
| `CodeIndexService#ensureIndexed` | `appId <= 0` | 不建索引 |

这个隔离是对的，它保证生成评测的口径跨版本可比，否则 metrics 会随 RAG 开关漂移。但它同时意味着跑批出来的通过率、自愈轮次与检索质量毫无关系，单测更不可能覆盖（全程 mock，测试环境的数据源是假值）。所以检索质量必须单独测，用真实的正数 appId 与真实的产物工程。

### 指标为什么按文件级

用户说「改一下导航栏」时，他指向的是一个文件，不是某几行。按片段级算会把命中了同一文件的其它片段判成漏召，分数低于真实体验。

### 语义型为什么是 20 条

为了够得着显著性，不是为了数字好看。

配对比较只看不一致对（同一条用例两组一组捞到一组没捞到）。v1.0 的 8 条语义型实测：仅关键词 4/8、仅向量 7/8，不一致对只有 3 个且全部偏向向量。两侧符号检验：

| 全偏向向量的不一致对 | 3（v1.0 现状） | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|
| 两侧 p | 0.2500 | 0.1250 | 0.0625 | 0.0312 | 0.0156 |

要 6 个不一致对才跨过 p<0.05。8 条样本下单条用例摆动 12.5 个百分点，再往下比较就是在拟合噪声。扩到 20 条才有机会把「方向明确」升级成「统计显著」。

这个 20 不是随口定的整数，是先算出阈值反推出来的样本量。后来实测兑现了：扩到 20 条后不一致对恰好 6 个且全部偏向向量，p = 0.031。

### 扩样本要覆盖中间地带

v1.0 里 `kw=0` 的极端样本（05、13）是词面与代码完全不重合的情形，最能拉开差距的其实是语义型但词面有轻微重合的那批。只收极端样本会把向量的收益算得过于乐观。

### 标注必须人工完成

不能用模型先生成一份期望文件，再拿它去评测模型自己的检索，那测的是模型与自己的自洽程度，与检索质量无关，而且分数通常还很漂亮。两个工程各 10 来个文件，标注一次半小时可完成。

### 语义型 query 含代码标识符为什么算配置错误

一条语义型用例只要写了文件名，它就退化成关键词题，却仍然被算进语义型的分母，语义型召回率被抬高、向量的增量收益被抹平，而报告里看不出异常。配置写错会让指标变成 0，谁都看得见；这个是让指标悄悄变好。点名型不受此规则约束，写文件名正是它的本分。

## 五、检索评测的历次实验记录

四轮实测的过程与结论。数字都来自当时的标注集版本，跨版本不可直接比较。

### 首轮：一次被缺陷抬高的成绩

第一次真跑（`ablation=false`，只跑线上权重）的数字：

| 配置 | Recall@8 | Precision@8 | MRR | 命中率 | 点名型 Recall@8 | 语义型 Recall@8 |
|---|---|---|---|---|---|---|
| 混合 0.7/0.3 | 93.8%（15/16） | 21.4% | 0.786 | 93.8% | 100%（8/8） | 87.5%（7/8） |

从逐条明细再算出来的两个数：Top-1 = 11/16（68.8%）；点名型 MRR 0.938，语义型 MRR 0.635，语义型 8 条里只有 4 条排首位。

这一轮不能当基线。症状是点名型 8/8 好得可疑，而用例 01 更矛盾：需求点名了 `Navbar.vue`，排第一的却是 `Attractions.vue`。

定位方式：`QueryTerms` 是纯函数，不依赖 Spring 与网络，可以直接 `javac` 出项目源码加一个探针类，把 16 条用例的术语、加分判定、关键词分全部离线复算一遍，再与线上报告对照。复算结果：

| 用例 | 术语里出现的扩展名词 | 被判「被点名」的文件数 | 全工程 .vue 文件数 |
|---|---|---|---|
| tour 的 4 条点名型 | `vue`（来自 `Navbar.vue` 等） | 8/14 | 8 |
| shop 的 4 条点名型 | `vue`；`products.js` 那条另含 `products` | 8~9/15 | 8 |

根因有两处，同一个主题：把扩展名当成了标识符。

1. `QueryTerms#extract` 会把 `Navbar.vue` 切成 `navbar` 和 `vue`；
2. `mentionsFile` 判定「被点名」用的是 `路径.contains(术语)`，于是 `vue` 命中每一条 .vue 路径，全工程 .vue 文件各得 `FILE_MENTION_BONUS = 0.5`。这个加成大于一整份加权得分（0..1）的一半，拿到就绝对领先，净效果成了「.vue 文件整体排在 .js/.css/.html 之前」。`products.js` 那条同理，驼峰拆出的 `product` 命中了 `products.js` 与 `Products.vue`。

加成对期望文件和它的竞争者同等生效，净差分为零。所以点名型 100% 不是加成的功劳，而是「所有 .vue 都被加分」加上「topK=8 不小于工程里的 .vue 文件数」的必然结果，这一列没有鉴别力。

修法（`QueryTerms`，2026-09-23）：扩展名词从术语里剔除（只剩扩展名时退回原集合，否则术语集为空会让检索器直接放弃检索）；`mentionsFile` 改为「术语与文件名主干归一化后相等」（大小写与 `-`、`_` 不参与比较），不再做路径子串匹配。目录名（`views`）与部分名（`product` 对 `products`）都不算点名。

预期是修复后点名型分数会下降，那才是正常值。修复前后两轮口径不同，不可直接比较。

### 首轮带出的三条读法修正

1. `Precision@8` 在该标注集下恒等于 `1 ÷ 返回文件数`（21.4% 与逐条吻合），与检索质量无关；命中率恒等于 `Recall@K`。报告里已加脚注。
2. 「向量是否参与打分」的旧证据（top-1 向量分 > 0）必然成立，换成 top-1 关键词分为 0 的条数。首轮该值 2/16（用例 05、13），这两条的首位排名只能来自向量。
3. 语义型的短板在排名不在召回。掉到第 3、4 位的两条，top-1 是 `src/styles/main.css` 与 `index.html` 这类对任何查询都有不低余弦的文件。后续值得验证的方向是给全局样式与入口文件加路径先验或长度归一，而不是继续调权重。样本只有 16 条时先不为它改算法。

### 第二轮：三组权重消融

修复后重跑 `POST /rag-eval/run`（默认 `ablation=true`），第一次拿到三组对照。

| 配置 | Recall@8 | MRR | 命中率 | 点名型 Recall / MRR / Top-1 | 语义型 Recall / MRR / Top-1 |
|---|---|---|---|---|---|
| 仅关键词(0/1) | 75.0%（12/16） | 0.750 | 75.0% | 100% / 1.000 / 8-8 | 50.0% / 0.500 / 4-8 |
| 仅向量(1/0) | 93.8%（15/16） | 0.786 | 93.8% | 100% / 1.000 / 8-8 | 87.5% / 0.573 / 3-8 |
| 混合(0.7/0.3) | 93.8%（15/16） | 0.818 | 93.8% | 100% / 1.000 / 8-8 | 87.5% / 0.635 / 4-8 |

修复生效了吗：生效了，但痕迹只在排名上。

上轮预期修复后点名型分数会下降，实测 Recall 没有下降。原因是 `topK=8` 已经覆盖工程里全部 .vue 文件，期望文件无论排第几都会出现在结果里，Recall 对这一缺陷不敏感。缺陷的唯一痕迹是排名：用例 01 的榜首从 `src/pages/Attractions.vue`（与本需求无关）回到期望的 `Navbar.vue`；点名型 MRR 从 0.938 升到 1.000，Top-1 从 7/8 升到 8/8。

这也说明上轮给分组补 MRR 与 Top-1 是必要的。只看 Recall，这一轮会被读成「修复没效果」。

结论一，向量是必要的，这是唯一一个量级可信的效应。语义型 Recall 从仅关键词的 50.0%（4/8）升到仅向量的 87.5%（7/8），差 37.5 个百分点、多召回 3 条。16 条用例里有 8 条只描述功能、不含任何代码标识符，纯关键词只能捞到其中一半。

结论二，混合取了两者的长处，不劣于任一单路。语义型上混合的 Recall 87.5% 追平仅向量，Top-1 4/8 追平仅关键词且高于仅向量的 3/8。也就是说 0.3 的关键词权重干了它该干的事：召回广度交给向量，榜首位置由关键词校准。单看仅向量那一列还能看到病根，召回 87.5% 却 Top-1 只有 37.5%，纯语义向量容易把 `main.css`、`index.html` 这类对谁都像的文件排到前面，关键词分把它们压了下去。

结论三，不要把 MRR 的组间差当成证据。

| 对比 | MRR 差 | 折算成「用例前进一名」 |
|---|---|---|
| 混合 0.818 vs 仅向量 0.786 | 0.032 | 约 1 条 |
| 混合 0.818 vs 仅关键词 0.750 | 0.068 | 约 2 条 |
| 混合语义型 0.635 vs 仅向量 0.573 | 0.062 | 约 1 条 |

MRR 是 16 条（分组仅 8 条）的平均，`0.032 × 16 ≈ 0.5`，恰好等于一条用例从第 2 名前进到第 1 名。这个量级在 8~16 条样本上就是噪声。能站住的只有结论一那个 37.5 个百分点。

结论四，点名型这一列已经饱和。三组（含仅关键词）全部是 100% / MRR 1.000 / Top-1 8-8，意味着连关键词单路都能满分，它无法支撑「`FILE_MENTION_BONUS` 有用」或「关键词权重 0.3 有用」这类结论。上轮的 100% 是缺陷的产物，这一轮的 100% 是任务太简单的产物，成因不同，结果一样。

所以权重不调，该改的是标注集。现有数据支持「保留向量高权重 + 保留一路关键词」，不支持「0.7 / 0.3 是最优」。要回答后者，得先让标注集有分辨力：

1. 点名型加干扰项。现在的点名型查询里，文件名主干（`navbar`、`productcard` 等）在工程内是独一无二的词，一次命中就到底。要测出加成是否会把错的那个顶上去，得让用例里出现相似竞争者（同时提到 `Products.vue` 与 `ProductCard.vue`，或利用两个工程各有一个的 `Navbar.vue` / `NavBar.vue`）。
2. 补多期望文件用例（如「导航栏和页脚一起改」）。现在清一色单个期望文件，导致 `Precision@K` 与命中率双双退化。
3. 语义型从 8 条扩到 20 条以上。分组样本 8 条时，MRR 的组间差异整个落在噪声量级，样本上去之前任何微调权重的结论都是拟合噪声。

第 3 条已落地，见下一节。第 1、2 条仍未做。

另有两个副产物。

增量索引确实生效：索引耗时从首轮 14937 ms 降到本轮 213 ms。两次之间工程文件没变，`fileHash` 比对全部通过，一个片段都没有重新向量化。

用例 16 的标注边界留待复核：`shop-detail-semantic-16` 在混合与仅向量两组都未召回 `Detail.vue`，top-1 是 `src/data/products.js`。尺寸数据确实写在 `products.js` 里，`Detail.vue` 只负责展示，而需求说的是「排得清楚些」，指向展示层，标注 `Detail.vue` 是合理的。它提示的是数据与展示分离这类需求本身有歧义，复核时应单独确认。

### 第三轮：扩到 28 条之后的消融

标注集升到 v1.1（28 条）后重跑 `ablation=true`。分母换了尺子，与第二轮不可直接比较。

| 配置 | 总体 Recall@8 | 总体 MRR | 点名型 Recall / MRR / Top-1 | 语义型 Recall / MRR / Top-1 |
|---|---|---|---|---|
| 仅关键词(0/1) | 75.0%（21/28） | 0.682 | 100% / 1.000 / 8-8 | 65.0%（13/20） / 0.554 / 10-20 |
| 仅向量(1/0) | 96.4%（27/28） | 0.759 | 100% / 1.000 / 8-8 | 95.0%（19/20） / 0.663 / 9-20 |
| 混合(0.7/0.3) | 96.4%（27/28） | 0.807 | 100% / 1.000 / 8-8 | 95.0%（19/20） / 0.729 / 11-20 |

结论一，跨过显著性门槛了，扩样本的目的达到。语义型上的配对比较：

- 仅关键词漏 7 条：`05、06、07、16、18、23、24`
- 仅向量漏 1 条：`16`
- 不一致对 6 个（05、06、07、18、23、24），全部偏向向量，反向 0 个

两侧符号检验 `p = 2 × (1/2)^6 = 0.031 < 0.05`。对照第四节的表，6 恰好就是跨线的位置，也就是说「扩到 20 条」这件事兑现了它被做出来的唯一理由。

结论二，数字变小了，但这是好事。语义型 Recall 从关键词的 65%（13/20）升到向量的 95%（19/20），差 30 个百分点；v1.0 是 50% 到 87.5%，差 37.5 个百分点。差距缩小不是退化，是扩样本时按计划补了中间地带，新增的 12 条里有多条关键词也能捞到（`kw` 在 0.03 到 0.15 之间），正是这些更接近真实分布的用例把上限压了下来。

结论三，残留问题换了形态，从捞不到变成排不前一。

- 漏召只剩 1 条（用例 16，三组都漏）。
- 语义型 20 条里只有 11 条排首位（55%），另有 8 条进了 Top-K 却落在第 2 到第 4 位。

新加的排后清单把榜首被谁占走汇总出来（混合组）：`src/styles/main.css` 4 次、`src/pages/About.vue` 3 次、`src/pages/Guide.vue` 1 次。8 条排后里 7 条被两个「通用文件」占走，首轮那个通用文件淹没的猜测被坐实，而且现在能点名：旅游站的 `main.css`、手办商城的 `About.vue`。

`About.vue` 为什么像（读源码确认）：整页是泛化的中文营销文案，品牌故事、核心优势、数据展示、联系方式，全文没有任何商品侧标识符，任何「关于这家店」的需求问它都不违和。

结论四，用例 16 不是标注错误，是一条真实的边界。复核源码后确认需求说的是「太挤了、想排得清楚些」，改的是 `Detail.vue` 里那三个规格卡片（比例、高度、材质）的排布；尺寸数据确实在 `products.js`，但这条需求不需要动数据，标注 `Detail.vue` 是对的。漏召的成因是 `products.js` 里 12 个商品的尺寸字段堆在一起，相关片段密度远高于 `Detail.vue` 里那一个小节，查询里的「手办」「多大」与数据文件高度重合。这说明「内容在数据文件、改动在展示文件」这类需求，检索会系统性地偏向数据文件，真要在产品上解决得把「改的是哪一层」也纳入打分。

结论五，点名型仍然饱和。三组（含仅关键词）依旧是 100% / 1.000 / 8-8。两轮下来这个结论很稳：`topK ≥ 工程文件数` 时点名型用例没有鉴别力。

这一轮改的代码是报告新增排后清单。理由就是结论三，MRR 与 Top-1 各只给一个数，看不出榜首被谁占走，而现在的残留问题恰恰是这个。按占位文件汇总而不是列用例号，因为要治的是那个文件。边界与漏召清单明确分开：漏召是期望文件没进 Top-K，排后是进了但没排首位，混在一起就分不清该补检索还是该治通用文件。

反向验证两路各自单独跑：把 `firstHitRank > 1` 退成 `>= 0`（把漏召也算进排后）恰好红 `aggregatesWhoStoleTheTopSpot`；把占位取自期望文件而非实得首位同样红该条。顺带修了一处测试数据缺陷，回退方向二起初红的是 `IndexOutOfBounds`，原因是测试用例缺 `expectedFiles`，异常同样来自「改错了地方」但看起来像数据不全，属于假信号。

下一步是换变量，不是继续加样本。扩样本的目的已经达成，继续加同类样本只会把 30 个百分点磨得更小。该做的是治通用文件那一项，但做之前先修正了它的前提，见下一节。

### 第四轮：横切文件折扣的验收判据被自己的数据否掉

把 `app.rag.generic-file-penalty` 设成 0.9 重跑 `POST /rag-eval/run?ablation=true`，其余一切不变，唯一变量就是这个系数。

这个开关当时只在 `application.yml` 里，而该文件被 `.gitignore` 排除，是本地配置、仓库里看不到；偏偏那时的报告头也没打印它，于是「这批数字是在折扣下跑的」这件事得靠翻配置文件才能确认。这个坑在下面处置一节里修掉了。

| 配置 | 总体 Recall@8 | 总体 MRR | 点名型 Recall / MRR / Top-1 | 语义型 Recall / MRR / Top-1 |
|---|---|---|---|---|
| 仅关键词(0/1) | 75.0%（21/28） | 0.682 | 100% / 1.000 / 8-8 | 65.0%（13/20） / 0.554 / 10-20 |
| 仅向量(1/0) | 89.3%（25/28） | 0.741 | 100% / 1.000 / 8-8 | 85.0%（17/20） / 0.638 / 9-20 |
| 混合(0.7/0.3) | 89.3%（25/28） | 0.804 | 100% / 1.000 / 8-8 | 85.0%（17/20） / 0.725 / 12-20 |

与第三轮（折扣关闭、同为 v1.1 的 28 条）逐项对照，同一把尺子，可以直接比：

| 指标 | 折扣关 | 折扣 0.9 | 变化 |
|---|---|---|---|
| 仅关键词（Recall / MRR / 语义型 / Top-1） | 75.0% / 0.682 / 65.0% / 10-20 | 逐项完全相同 | 0 |
| 仅向量 Recall@8 | 96.4% | 89.3% | −7.1pp |
| 混合 Recall@8 | 96.4% | 89.3% | −7.1pp |
| 混合 MRR | 0.807 | 0.804 | −0.003 |
| 混合语义型 Top-1 | 11/20 | 12/20 | +1 |
| 漏召 | 1 条（`…-16`） | 3 条（`…-13`、`…-16`、`…-18`） | +2 |
| 排后（混合） | 8（`main.css`×4、`About.vue`×3、`Guide.vue`×1） | 5（`Guide.vue`×2、`package.json`×1、`About.vue`×2） | −3 |

结论一，折扣确实没碰关键词路径。仅关键词那一列五项指标逐项零变化，精确到小数点。`genericFilePenalty` 只乘在向量项上（`score = vectorWeight × vectorScore × penalty + keywordWeight × keywordScore`），权重为 0 时乘任何系数都是 0。这条当初写在注释里的设计约束得到了实证，它同时是下面那个归因的旁证：既然关键词组一动没动，向量组掉的那两条就必然落在被折扣的集合里。

结论二，按预设判据不通过。写代码之前定下的验收表是两行：排后清单的榜首占位要下降，漏召清单条数不能增加。实测排后达标（`main.css` 占位 4 降到 0），漏召从 1 涨到 3，启用条件不成立。这不是事后找补，那张表在改代码之前就写下了，当时说好「若变长说明折扣压过了它该保护的召回」。

结论三，新增的两条漏召期望文件都是 `src/App.vue`。

| 用例 | 需求 | 期望 | 本轮实得 |
|---|---|---|---|
| `shop-app-semantic-13` | 页面最底下那行版权信息，想补上完整的公司名称 | `src/App.vue` | About.vue、Home.vue、NavBar.vue、Products.vue |
| `tour-transition-semantic-18` | 在几个页面之间切换的时候内容太生硬了，希望有个淡入淡出的过程 | `src/App.vue` | Home.vue、Attractions.vue、Guide.vue、About.vue |

两条都是语义型，没写文件名，拿不到点名豁免；而 `src/App.vue` 的主干 `app` 恰好属于入口名，向量分被乘了 0.9，于是掉出 Top-8。

判据错在把「位置恒定」当成了「内容泛化」。全局样式（`css`、`scss` 等）是横切关注点，内容真的泛化，任何界面需求都沾边，这一半被数据支持；入口名（`main`、`index`、`app`）只是路径固定，内容并不泛化，`App.vue` 承载的是根布局、页脚、路由过渡，而上面这两条需求恰好就落在这些地方，它是正确答案，不是对谁都像。

回头看当初写这条判据的理由：「`main.js`、`App.vue`、`index.html` 在任何 Vue 工程里都是入口，按它们降权不属于为某个工程调参」。这句话本身没错，但它证明的是判据可移植，而不是这些文件该降权。可移植的判据照样可以是错的判据，当时把「不是过拟合」当成了「方向正确」，少问了一句「它们真的泛化吗」。

另外上一轮的风险预警猜错了对象。当时预言 17 号的 `main.css` 会掉出 Top-K，实测没有发生，它仍排第 2；伤在一个完全没预料到的位置。知道「会伤到某个期望文件」是稳的，能精确到哪一条则是运气。

结论四，只看排后清单会主动骗你。排后从 8 降到 5，看着像成功，但那 3 条里有 2 条不是改善，是退化成漏召（13、18 号）。两个清单的差值是同一批用例在两个状态之间的迁移，排后条数的下降本身就可能是漏召条数上升的镜像。任何只报告单一清单的读法都会得出与事实相反的结论，而按当初的验收表，先看排后恰恰是被推荐的第一眼。

净账是 Top-1 加 1 换 Recall 减 2。按已有的论证，排后的代价接近于零（Top-K 没占满，被抢首位的期望文件照样进上下文，它占的是字符预算与模型注意力），漏召的代价是正确文件彻底不在列表里。这是拿零代价的东西换了真代价。

结论五，榜首位置是竞争性的，压下一个总有下一个补位。17 号（「网站的默认字体加载太慢，想换成系统自带的」，期望 `src/styles/main.css`）本轮实得：

```
package.json、src/styles/main.css、vite.config.js、src/components/Footer.vue、src/pages/Home.vue
   ↑ kw=0（纯向量）      ↑ 期望文件，第 2 位
```

折扣把 `main.css` 从榜首压下去之后，榜首交给了 `package.json`。它不在任何一条判据里（既不是样式，也不叫 main、index、app），而「字体加载慢」这类需求与依赖清单的语义相关度天然不低，字体包就写在 `dependencies` 里。路径先验的天花板在这里：你只能压掉你认得出名字的文件，而榜首总会被下一个泛化文件占据。要真正解决得引入内容判别力度量，而不是继续给文件名单打补丁。

处置有三条：

1. `QueryTerms#isGenericFile` 删掉入口名判据，只保留全局样式，`GENERIC_ENTRY_NAMES` 与 `ENTRY_EXTENSIONS` 两个常量一并删除，`entryFilesAreNotGeneric` 这个测试用例接替原来的 `frameworkEntryNamesAreGeneric`。
2. 折扣保持默认关闭（`application.yml` 改回 1.0，并补上 `APP_RAG_GENERIC_FILE_PENALTY` 环境变量出口）。收窄后它的收益仍然接近零，它治的是排后，而排后在当前工程规模下代价接近 0。它的定位是工程变大、文件数逼近 Top-K 时的预防手段。
3. 报告头打印折扣系数（`通用文件折扣=0.90` 或 `=1.0（关闭）`）。开头那个得去翻配置文件的窘境不该出现第二次，报告不自证配置，跨批次比较就没法做。

反向验证两路都是干净的断言失败：把入口名判据加回，恰好红 `entryFilesAreNotGeneric`；去掉报告头那一项，恰好红 `printsGenericFilePenalty`。均已还原。

### 一条方法论

判据可移植不等于判据方向正确。选入口名作判据的理由是「任何 Vue 工程都有 main、index、App，不算为本工程调参」，这话本身没错，但它只反驳了过拟合，没回答该不该降权。可移植的错判据比过拟合更难被发现，因为它以讲道理的面目出现。用任何先验之前要问的是这个文件属于哪一类（内容泛化，还是只是路径固定），而不是这条规则能不能搬到别的工程。
